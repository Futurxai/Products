# domain/

The innermost Clean Architecture layer. **No Angular imports, no Firebase imports, no framework of any kind.** Pure TypeScript only — this is what makes the scoring/lifecycle rules trivially unit-testable and portable if the module is ever embedded in a different host platform.

- `models/` — plain interfaces/types: `PuzzleExperience`, `Question` (`QuestionDefinition`, the Creator's full authoring shape, and `RecipientQuestionView`, M4's deliberately-narrower `{questionId, prompt}` projection — see `rules/recipient-view.rules.ts`), `Progress`, `Score`, `Creator`, `AuthUser`. Data shapes, no behavior.
- `rules/` — pure functions only: `computeScore()`, `starRatingFor()`, `starLabelFor()`, `canEdit()`, `canPublish()`, `isAnswerCorrect()`, `isValidEmail()`, `passwordStrength()`, `groupExperiencesForDashboard()`, `summarizeDashboard()`, `wizardStepCompletion()`, `validateImageFile()`, `recipient-view.rules.ts`'s `toRecipientQuestionView()` (M4 — the one place a full `QuestionDefinition` is narrowed to what a Recipient may see, called server-side by `resolveShareToken`), and `gameplay.rules.ts`'s `submitAnswerAttempt()` / `revealNextClue()` / `resolvePartnerHelp()` (M3 Feature 4) — the pure "play one question" state machine used by the ephemeral Creator Preview only (it needs the full `QuestionDefinition`, which the real Recipient client is never given). The real M4 Recipient flow instead calls the actual Cloud Functions for every gameplay decision, reusing only the UI-gating rules (`canRequestPartnerHelp`, `computeScore`, `isExperienceComplete`) against real `puzzle_progress` data. Given the same input, always the same output. No side effects, no I/O.
- `errors/` — `DomainError` and its subclasses (`TokenNotFoundError`, `IncompleteExperienceError`, etc.), each carrying a typed `code: DomainErrorCode`; and, separately, `AuthError` and its subclasses (`InvalidCredentialsError`, `EmailAlreadyInUseError`, etc.), each carrying a typed `code: AuthErrorCode` — kept as two hierarchies, not one, because one enumerates Cloud-Function business failures and the other enumerates Firebase Auth SDK failures, and conflating them would make error codes ambiguous about which system produced them. Thrown by `application/` use-cases when a business precondition isn't met; mapped to an `HttpsError`/HTTP response at the Cloud Functions callable boundary, or a UI message in Angular — the domain layer itself has no idea either of those exist.
- `ports/` — interfaces the domain/application layers depend on:
  - **Client-facing** (Angular, M3/M4): `ExperienceRepositoryPort`, `ProgressRepositoryPort`, `PuzzleApiPort`, `AuthPort`, `CreatorRepositoryPort`, `RecipientSessionPort` — simple CRUD/read + a realtime `watch()`/`authState()`. `AuthPort` (Firebase Auth identity/session) and `CreatorRepositoryPort` (Firestore profile document) are deliberately separate interfaces — Auth owns "who is signed in," Firestore owns the app-specific profile fields, and neither should have to fake the other's data. `RecipientSessionPort` (M4) is deliberately a third, separate interface from `AuthPort` rather than a reuse of it — a Recipient's anonymous, experience-scoped custom-token session shares no shape with a Creator's email/Google identity.
  - **Server-facing** (Cloud Functions, M2): `ExperienceStorePort`, `ProgressStorePort` — atomic, business-named operations (`markPublished`, `resolvePiece`, ...), each implemented with a Firestore transaction where concurrent writes are possible. Deliberately a *different* interface shape from the client ports, not a shared one forced to fit both — a client read and a server transactional write are genuinely different operations.

`infrastructure/` implements all of the above; `domain/` and `application/` never know or care that the implementation happens to be Firebase.

Enforced by the `no-restricted-imports` ESLint rule in `.eslintrc.json` — importing `firebase/*` or `@angular/fire/*` anywhere under this folder is a lint error, not just a convention.

Populated in Milestone M1 (models/rules/client ports), M2 (errors/server ports), and M3 (auth model/errors/rules/ports; dashboard grouping/summary rules; wizard step-completion/image-validation rules). Every file in `rules/` and `errors/` has a matching `.spec.ts` — these are pure, I/O-free, so there's no excuse for untested branches.

**This folder is the single authored source.** `apps/puzzle-module/functions/src/domain/` is a *generated* copy (gitignored, regenerated by `npm run sync-domain` before every functions build/test) — never hand-edit anything there. See `functions/README.md` for why a build-time copy was chosen over a shared npm package.
