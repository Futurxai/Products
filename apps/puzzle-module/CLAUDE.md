# Puzzle Module — App Context

What it does: Personalized 3×3 photo-jigsaw gifting experience — a Creator authors 9 memory-based questions gating a reveal image; a Recipient plays through a shared link with no account required.
Target user: Couples, friends, and family in India personalizing a digital gift for an occasion (anniversary, birthday, proposal, wedding, friendship, baby, graduation, long distance, family).
Key features: Creator authoring wizard, secure token-based recipient links, clue system with WhatsApp partner-help fallback, server-validated scoring, PWA-first.
Firebase project: `lovedigitally-puzzle` — a dedicated project (migrated off the shared `lovedigitally-app` project per ADR-0011, which supersedes the original ADR-0001/ADR-0007 shared-project-and-symlink architecture). The Puzzle Module owns its own Firestore/Storage rules, its own Storage bucket (`lovedigitally-puzzle.firebasestorage.app`), and its own Hosting site + Functions codebase (`puzzle-module`, unchanged naming). No longer shares any Firebase infrastructure with `/lovedigitally-web`.
Architecture: Clean Architecture — `domain/` (framework-free models & rules) → `application/` (use-cases & signal facades) → `infrastructure/` (Firebase adapters) → `features/` (Ionic Angular standalone pages). See `docs/puzzle-module/` at the repo root for the full PRD, Module Contract, and architecture spec this app is built against.

App-specific rules:
- `domain/`, `application/`, `features/`, `shared/` (Angular app) must never import `firebase/*` or `@angular/fire/*` directly — only `infrastructure/firebase/*` may (enforced by ESLint, see `.eslintrc.json`). The `functions/` codebase has its own equivalent boundary: only `functions/src/infrastructure/*` touches `firebase-admin`.
- Correct answers, clue text, and the full-resolution reveal image are never sent to the client before earned — always validated server-side via Cloud Functions, never trust the client (Module Contract §8). This is enforced, not just documented: image slices only exist as separate Storage objects served via short-lived signed URLs minted after a piece is confirmed earned.
- The Recipient never sees a login screen — Firebase Anonymous Auth is minted silently by `resolveShareToken`, scoped to one experience via a custom claim (`request.auth.token.experienceId`), verified by both application code and Firestore Rules.
- `firestore.rules` and `storage.rules` in this directory are standalone files, owned entirely by this app (ADR-0011) — previously symlinks into `../../lovedigitally-web/` when the two apps shared a Firebase project (ADR-0001/ADR-0007, both now superseded). They no longer share an inode or a deploy with `lovedigitally-web`'s rules; a change to one never affects the other.
- `functions/src/domain/` is a generated copy (`npm run sync-domain`, gitignored) of `src/app/domain/` — the canonical domain layer is hand-edited in exactly one place.
- Cloud Function business-rule failures resolve as `{ ok: false, error, message, details }` (matching `PuzzleApiPort`'s `ApiFailure`), not as rejected promises — only genuine bugs/infra failures reject. See `functions/src/callable/define-callable.ts`.
- Every callable deploys to `asia-south1`, not the Firebase default (`us-central1`) — `app.config.ts`'s `provideFunctions()` must request that region explicitly (`getFunctions(getApp(), 'asia-south1')`) or `httpsCallable` silently resolves against a deployment that doesn't exist.
- A `PuzzleExperience` is always split across two Firestore documents — `puzzle_experiences/{id}` (public: `creatorId`, `occasion`, `emotion`, `recipientDisplayName`, `status`, `welcomeNote`, `lockedPatternImagePath`, `createdAt`/`publishedAt`/`completedAt`/`archivedAt`) and `puzzle_experiences_private/{id}` (owner-only: `shareTokenHash`, `completionMessage`, `partnerHelpChallenge`, `revealImagePath`, `questions`). `functions/src/infrastructure/firestore-experience.store.ts` (Admin SDK) and `src/app/infrastructure/firebase/firestore-experience.repository.ts` (client SDK) both implement this exact same split — keep them in agreement if either ever changes. `status`/`publishedAt`/`completedAt`/`archivedAt`/`shareTokenHash` are Cloud-Function-only writes (enforced by Firestore Rules, not just convention).
