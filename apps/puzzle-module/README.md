# Puzzle Module

Ionic Angular (standalone components + Signals) PWA for the Love Digitally Puzzle Module. See `docs/puzzle-module/` at the repo root for the full PRD, Module Contract, Phase 4 UI/UX spec, and Phase 5/6 architecture and roadmap this app implements.

## Status

**M5 Phase 2 — Performance complete.** M0 (scaffold/CI), M1 (domain layer), M2 (all 6 Cloud Functions + image-slice trigger), M3 (all five Creator UI features), M4 (all seven Recipient Experience phases), M5 Phase 1 (analytics instrumentation), and M5 Phase 2 (performance optimization) are done and fully validated. Next: M5 Phase 3 — Accessibility.

Note on numbering: earlier in-repo comments referred to the Recipient milestone as "M5"/"M6" before the Recipient build was scoped in detail — this doc, and all Recipient-facing code comments, now use the milestone's actual name, **M4**.

See `functions/src/` for the Cloud Functions codebase: `schemas/` (Zod), `callable/` (thin onCall wrappers), `application/` (use-cases), `infrastructure/` (Firestore/Storage/Auth adapters), `triggers/` (reveal-image slicing), `emulator-tests/` (real Firestore+Auth+Storage emulator coverage, run via `npm run test:emulator` inside `functions/`).

### Creator Authentication (M3, Feature 1)

- **Pages** (`src/app/features/creator/auth/`): `login/`, `signup/`, `forgot-password/`, sharing a feature-local `ui/auth-shell.component.ts` layout.
- **Design system** (`src/app/shared/`): `button/`, `input/` (a `ControlValueAccessor` wrapping `ion-input`), `card/`, `toast/` (signal-based queue + host, mounted once in `AppComponent`), `loader/` — thin, opinionated wrappers over Ionic primitives rather than hand-rolled controls. The rest of the Phase 4 component set is added incrementally as later features need it, not built ahead of a consumer.
- **Auth architecture**: `AuthPort` (Firebase Auth identity) and `CreatorRepositoryPort` (the `puzzle_creators` Firestore profile) are deliberately separate ports — Auth owns the session, Firestore owns app-specific profile fields. `AuthUseCase.resolveProfile()` provisions a Creator's Firestore doc on first sight (fresh sign-up, or a first-time Google sign-in) and self-heals it on every session restore if it's ever missing. `AuthFacade` is the Signal store pages and `creatorAuthGuard`/`guestGuard` actually consume — it waits for `authReady()` before either guard makes a redirect decision, so a page refresh mid-session-restore never flashes a false redirect to `/auth/login`.
- Every Firebase Auth error is mapped to a typed `AuthError` subclass (`domain/errors/auth-errors.ts`) with an already-UI-ready message — pages never see a raw `FirebaseError`.
- The production bundle budget (`angular.json`) was raised from 750kb/950kb to 900kb/1.1mb warning/error — the increase reflects real, necessary weight (Firebase Auth/Firestore's modular functions are now actually *called*, not just provided; more Ionic form components), not unreviewed bloat; still enforced, just recalibrated.

### Creator Dashboard (M3, Feature 2)

- **Page** (`src/app/features/creator/dashboard/dashboard.page.ts`): replaces the Feature 1 placeholder. Welcome header with a profile-menu popover (sign out), an Analytics Summary card (total/draft/published/completed counts), and Draft/Published/Completed sections rendering `ui/experience-card.component.ts` items. Loading/error/empty states are all real, driven by `CreatorDashboardFacade`.
- **"Create New Puzzle" opens the Wizard** at `/creator/wizard/new`, and draft cards are clickable to resume editing at `/creator/wizard/{experienceId}` — both wired in Feature 3. Published/completed cards stay non-interactive: there's no Preview/detail destination for them yet (Features 4-5).
- **`FirestoreExperienceRepository`** splits/merges every `PuzzleExperience` across `puzzle_experiences` (public) and `puzzle_experiences_private` (owner-only) — the exact same schema `functions/src/infrastructure/firestore-experience.store.ts` (M2) already reads/writes via the Admin SDK. `update()` only ever touches Wizard-editable fields (`revealImagePath` is explicitly excluded — trigger-only, see Feature 3 below); status transitions stay Cloud-Function-only. The `listByCreator` query (`where(creatorId==).orderBy(createdAt desc)`) was verified directly against the real Firestore emulator before being relied on, rather than assumed — no extra composite index turned out to be needed beyond Firestore's automatic indexing for this shape.
- **Dashboard grouping/summary** (`domain/rules/dashboard.rules.ts`) is framework-free and unit-tested on its own — `published` and `in_progress` are grouped together (both read as "live" to a Creator), `archived` is excluded entirely (no archive view yet).

### Puzzle Creation Wizard (M3, Feature 3)

- **`WizardPage`** (`src/app/features/creator/wizard/wizard.page.ts`), routed at `/creator/wizard/:experienceId`: resolves the `new` sentinel by minting a fresh draft (`crypto.randomUUID()`) and replacing the URL with the real id, or loads an existing draft to resume. Renders a `StepperComponent`, autosave status text, and the current step via `@switch` over `PuzzleWizardFacade.currentStep()`. Step navigation is always free (never gated on completion) — the true hard gate is the eventual Publish action (Feature 5), via the pre-existing `canPublish()`.
- **Six steps** (`features/creator/wizard/steps/`): Occasion & Emotion, Image Upload (with a hand-rolled canvas pan/zoom cropper, `ui/image-cropper.component.ts` — no third-party dependency, to avoid further bundle pressure and to keep full control over accessibility), Recipient Details, Questions (exactly 9, each with up to 3 clues via `ui/question-editor.component.ts`), Completion Details, and a read-only Review summary. "Preview experience" now opens the real Puzzle Preview (Feature 4, below); "Publish" stays deliberately inert beyond a toast — Feature 5 isn't built yet.
- **`PuzzleWizardFacade`** (`application/creator/puzzle-wizard.facade.ts`) owns all wizard state as Signals and debounced autosave (800ms, optimistic local merge + retry on failure) — every meaningful change is saved without an explicit "Save" action.
- **Unsaved-change protection** is two-layer: `wizardUnsavedChangesGuard` (`CanDeactivateFn`, covers in-app Router navigation) plus a `beforeunload` listener on `WizardPage` (covers real tab close/refresh, which Router guards never see).
- **Image upload**: `StorageUploadPort`/`FirebaseStorageUploadService` upload the creator's cropped original to `puzzle_storage/{creatorId}/{experienceId}/reveal-image-original.{ext}`. The Wizard only ever shows a local `URL.createObjectURL()` preview of what was just cropped — Storage Rules only grant a Creator read access to their own original upload, never the server-processed `reveal-image.jpg` that `revealImagePath` points to (set asynchronously by the `onRevealImageUploaded` Cloud Function trigger).
- The production bundle budget (`angular.json`) was raised from 900kb/1.1mb to 1.35mb/1.6mb warning/error — the increase reflects the Wizard's real new weight (canvas cropper, 6 step components, Storage SDK usage now actually exercised), not unreviewed bloat; still enforced, just recalibrated.

### Puzzle Preview (M3, Feature 4)

- **`PreviewPage`** (`src/app/features/creator/preview/preview.page.ts`), routed at `/creator/preview/:experienceId`, reached from the Wizard Review step's "Preview experience" button (which flushes any pending autosave first, so Preview never reads stale data). "Back" returns to that same experience's Wizard Review step, not the Dashboard — Preview is a detour from the Wizard, not a separate destination.
- **A Creator plays through their own draft exactly as a Recipient would** — locked 3×3 board, question modal, answer submission, correct/incorrect feedback, clue ladder, the "Ask Your Partner" fallback (challenge text + a WhatsApp share link + an immediate reveal), a star-rated completion screen, and the final reveal image. All of it is deliberately ephemeral: `PuzzlePreviewFacade` (`application/creator/puzzle-preview.facade.ts`) holds everything in memory only and never touches `puzzle_progress` or a Cloud Function — a Creator's practice run must never be mistaken for real Recipient analytics.
- **Zero duplicated gameplay logic.** `domain/rules/gameplay.rules.ts` is the single pure "play one question" state machine — `submitAnswerAttempt`, `revealNextClue`, `resolvePartnerHelp` — deliberately shaped to mirror what `functions/src/application/{submit-answer,request-clue,request-partner-help-reveal}.usecase.ts` (M2) already do, minus the parts that only make sense with a real persisted session (Firestore transactions, the answer-attempt rate limiter, signed piece-image URLs). Preview calls these functions directly for its own ephemeral, local play-through; the real M4 Recipient client (below) does NOT reuse this file at all — it's never given a `QuestionDefinition` to run these rules against in the first place. `starLabelFor` (added to `domain/rules/scoring.rules.ts`) replaced an inline copy of the same completion-screen copy that had been living directly in `get-completion-summary.usecase.ts` — a small, safe, behavior-preserving extraction to the single source of truth, verified against the full functions unit + emulator suite.
- **The board image is never fetched through the Recipient's signed-URL pipeline.** `StorageUploadPort.getRevealImageOriginalBlob()` reads back the Creator's own `reveal-image-original.*` upload (the one object Storage Rules already grant them read access to) and reveals it piece-by-piece via CSS `background-position` slicing — cheap, since the Wizard's cropper always exports a square 1200×1200 image, so a uniform 3×3 grid needs no aspect-ratio math. This is not a security bypass: the boundary Module Contract §8 protects is Recipient-facing (never send the full image before it's earned); a Creator previewing their own authored puzzle already knows the whole picture, so there's no boundary to cross. The real Recipient flow (M4, below) stays built entirely on the separate server-side-sliced/signed-URL pipeline (M2) — Preview doesn't touch it.
- **`ModalComponent`** (`shared/modal/`) — the first `shared/` addition since the Wizard's design system work, wrapping `ion-modal` with `keepContentsMounted` so its projected content survives open/close cycles predictably (and is actually testable). Its first consumer is the Question modal.

### Publish & Share (M3, Feature 5)

- **`PublishPage`** (`src/app/features/creator/publish/publish.page.ts`), routed at `/creator/publish/:experienceId`, reached from the Wizard Review step's "Publish" button (which also flushes pending autosave first). `PublishExperienceFacade` runs the whole sequence: fresh-fetch the experience (so an async image-slice completion since the Wizard was last open is never missed), validate locally with the same `canPublish()` domain rule the Cloud Function re-checks server-side, and — if valid — call the real `publishExperience` Cloud Function through the newly-implemented `PuzzleApiPort`. **No server logic is duplicated or reimplemented client-side** — publishing, share-token generation, and image slicing (already triggered automatically at upload time by M2's `onRevealImageUploaded`) all stay exactly where M2 built them.
- **Three outcomes, three views**: a friendly validation-errors list (`publish-validation.util.ts` maps `canPublish()`'s machine field paths like `questions.q4.correctAnswer` to plain sentences) with a "Back to Wizard" action; a typed error view that distinguishes a business-rule failure's server-authored message (e.g. `UNAUTHORIZED`) from a generic, Retry-able message for a genuine network/Cloud-Functions-unavailable/permission-denied failure; or the Share screen.
- **The Share screen** (`ui/share-panel.component.ts`): the live share URL, a client-side-generated QR code (`shared/qr-code/`, via the `qrcode` npm package — never a third-party "QR image API," since that would leak the puzzle's secure share token to a service this app doesn't control), Copy Link (Clipboard API), WhatsApp Share, the Web Share API when `navigator.share` is available (progressive enhancement), an honestly-labeled "Share Stats — coming soon" placeholder (no fabricated numbers), "Preview as Recipient" (navigates to the existing Feature 4 Preview route — reused, not duplicated), and "Go to Dashboard."
- **`FirebaseFunctionsPuzzleApiService`** (`infrastructure/firebase/functions-puzzle-api.service.ts`) implements all six `PuzzleApiPort` methods against the real M2 callables, all in `asia-south1` — the region every Cloud Function actually deploys to. `app.config.ts`'s `provideFunctions()` was previously calling `getFunctions()` with no region at all, silently defaulting to `us-central1`; this went unnoticed until now because no earlier feature ever called a real Cloud Function from the client. Every method maps the raw wire response into the port's declared shape field-by-field rather than trusting a cast — the gameplay callables' own usecases use `questionId` internally while the port's client-facing types use `questionIndex` (the Phase 3 API contract's name), a real naming difference a blind cast would get wrong. `publishExperience`'s Cloud Function output was also missing the `status: 'published'` field the port's type already declared — a small, safe addition to `functions/src/application/publish-experience.usecase.ts`, verified against the full functions unit + emulator suite. Only `publishExperience` was exercised by this feature at the time; the other five methods were implemented and unit-tested in full, and are now the actual production path for M4's Recipient Experience (below).

### Recipient Experience (M4)

- **`/e/:shareToken`** (`src/app/features/recipient/experience.page.ts`) is the Recipient's entire app — deliberately the only route (see `app.routes.ts`), with Welcome/Board/Question/Completion handled as internal state switching rather than child routes, per the Phase 4 Navigation spec: there is no URL to skip ahead with. No header, no back button — unlike every Creator page, a Recipient never navigates here from elsewhere in this app.
- **Every gameplay decision comes from the real Cloud Functions, never a local check.** `PuzzleSessionFacade` (`application/recipient/puzzle-session.facade.ts`) calls `resolveShareToken`, `submitAnswer`, `requestClue`, `requestPartnerHelpReveal`, and `getCompletionSummary` through `PuzzleApiPort` for every correctness/scoring/clue/reveal decision — this is the architectural line that separates M4 from M3 Feature 4's Preview. The Recipient client is never handed a `QuestionDefinition` (with `correctAnswer`/`clues`) at all: `resolveShareToken`'s response carries only `RecipientQuestionView { questionId, prompt }` (`domain/models/question.model.ts`), a type that structurally cannot leak them (Module Contract §8, enforced at the type level, not just by convention — see `domain/rules/recipient-view.rules.ts`).
- **Legitimate domain-rule reuse, kept narrow.** The client reuses only UI-gating rules run against REAL `puzzle_progress` data for instant feedback — `computeScore`/`isExperienceComplete` (`PuzzleSessionFacade.score()`/`isComplete()`) and `canRequestPartnerHelp` (`canRequestPartnerHelpForActive()`, once the client has learned a question's true authored clue count from a `requestClue` response) — never as a second source of truth for correctness. `gameplay.rules.ts` itself (Preview's local state machine) is never imported here.
- **Two resolveShareToken contract gaps, found and fixed while building this milestone, not duplicated business logic.** (1) `publicMeta.questions`/`partnerHelpChallenge` — `puzzle_experiences_private` is owner-only in Firestore Rules with no recipient exception, so `resolveShareToken` was the only place that could ever hand a Recipient the prompt text and partner-help challenge; extended once, server-side. (2) `unlockedPieceImages` — a piece's signed image URL was otherwise only ever returned once, inside the `submitAnswer`/`requestPartnerHelpReveal` response that unlocked it; without re-signing already-unlocked pieces' URLs at resolve time, reopening a share link mid-game would show correctly-unlocked tiles with nothing to render. Both verified against the full functions unit + emulator suite before any client code was built against them.
- **Session-local limitation, documented not hidden**: revealed clue TEXT does not survive a page reload (nothing re-sends it — `puzzle_progress` only ever stores `cluesUsed`, a count). The clue counter (`X/3`) still reflects real progress after a reload; the UI shows a plain-language note instead of silently losing the clues.
- **`RecipientSessionPort`** (`domain/ports/recipient-session.port.ts`) is a third, deliberately separate identity port alongside `AuthPort` — a Recipient's anonymous, experience-scoped custom-token session (minted by `resolveShareToken`, no login screen ever shown) shares no shape with a Creator's email/Google identity.
- **Phases, in build order**: Entry (token resolve, anonymous auth, invalid/expired link, loading) → Welcome (avatar, story, Start button) → Puzzle Board (3×3 grid, question modal, answer submission, unlock animation) → Progress (progress bar, running score, star rating wired for completion) → Clues (sequential, capped at 3, visual counter) → Partner Help (challenge display, WhatsApp share, reveal) → Completion (final piece unlock, full-image reveal animation, star rating, completion message, celebration animation). Every phase ships with unit + component tests exercising the real gameplay paths, not just the happy path.

### Analytics (M5, Phase 1)

- **`puzzle_events` is write-only from Cloud Functions** (`allow write: if false` in `firestore.rules`) — a Recipient client can never write an analytics document directly, so every event is either a side effect of a server operation that already exists, or routed through one deliberately narrow new callable.
- **Nine of the eleven requested moments are logged as side effects of the Cloud Function that already authoritatively performs them** — no new endpoints, no duplicated business logic: `resolveShareToken` logs `recipient.link_opened` (covers both "Puzzle Opened" and "Share Link Opened" — the same real-world moment, not two events); `submitAnswer` logs `question.answered_correct`/`question.answered_incorrect` and, on a correct answer, `piece.unlocked`; `requestClue` logs `hint.used`; `requestPartnerHelpReveal` logs `partner_help.resolved` and `piece.unlocked`. `puzzle.completed` (with `finalScore`/`starRating`/`timeToCompleteMs`) is logged exactly once, at the precise `submitAnswer`/`requestPartnerHelpReveal` call whose `ProgressStorePort.resolvePiece()` result actually flips `status` to `'completed'` — never re-derived from `getCompletionSummary`, which a client may call more than once (retries, reloads).
- **The two purely client-observable moments with no server call to hang off of** — "Welcome Viewed" and the completion celebration rendering — go through a new, narrowly-scoped `logRecipientEvent` callable (`functions/src/callable/log-recipient-event.callable.ts`). Its Zod schema (`schemas/log-recipient-event.schema.ts`) allowlists a closed `z.enum(['recipient.welcome_viewed', 'celebration.viewed'])`, not `z.string()` — a Recipient can never claim an arbitrary or consequential event name like `puzzle.completed`; verified directly against the real Firestore + Auth emulators, including that an out-of-allowlist name is rejected before it ever reaches Firestore.
- **Analytics is best-effort, never allowed to break gameplay.** `logEventSafely` (`functions/src/application/analytics.ts`) awaits the Firestore write but swallows any failure — Cloud Functions v2 doesn't guarantee un-awaited work survives past the handler's return, so "best-effort" here means "try once, log and swallow the failure," not true fire-and-forget. Client-side, `PuzzleSessionFacade.logRecipientEventSafely()` mirrors the same guarantee across the network hop: `resolveLink()` fires `recipient.welcome_viewed` and `loadCompletionSummary()` fires `celebration.viewed`, both `void`-called with the rejection swallowed, never blocking or erroring the UI.
- **`AnalyticsEvent`/`AnalyticsEventName`** (`domain/models/analytics-event.model.ts`, synced into `functions/src/domain/` like every other domain type) matches the Module Contract §6 envelope exactly (`eventId`, `eventName`, `experienceId`, `moduleType`, `actorRole`, `timestamp`, `payload`) and deliberately only wires 9 of the full event list in `docs/puzzle-module/test-data/06-analytics-events.json` — Creator-side (`puzzle.created`/`published`/etc) and illustrative-only names are left unwired, not fabricated to look complete.

### Performance (M5, Phase 2)

- **Lazy loading**: already in place since M3/M4 — every top-level route (`app.routes.ts`) loads its page via `loadComponent()`, so `main-*.js` only ever ships the app shell + router + Firebase providers; each Creator/Recipient page is its own lazy chunk (confirmed in the production build's "Lazy chunk files" table — `wizard-page`, `publish-page`, `experience-page`, `preview-page`, `dashboard-page`, the three auth pages, all separate). Nothing changed here — Phase 2 verified it, didn't need to add it.
- **PWA caching — the one real gap this phase found and closed.** Despite "PWA-first" being a stated goal since M0, no service worker was ever wired up. Added `@angular/service-worker` (`ng add @angular/pwa`, then hand-corrected the generated formatting/paths to match this app's conventions): `ngsw-config.json` prefetches the app shell (`index.html`, `assets/manifest.webmanifest`, JS/CSS bundles) and lazily caches static assets (images, fonts) with a `prefetch` update check; `provideServiceWorker('ngsw-worker.js', { enabled: !isDevMode(), registrationStrategy: 'registerWhenStable:30000' })` in `app.config.ts` — disabled outside production builds so the emulator/dev workflow is never served stale cached responses, and registration deliberately deferred 30s past app-stable so the service worker never competes with the Recipient's first paint for network/CPU on a low-end device. **Deliberately no `dataGroups`** — Firebase Storage's signed piece/reveal-image URLs are short-lived and uniquely signed per request; caching them via the service worker would risk serving an expired signature. The existing in-memory cache (`PuzzleSessionFacade._pieceImages`) is the correct, already-present boundary for that; the service worker only owns the static app shell.
- **App icons**: `src/assets/icon/icon-{72,96,128,144,152,192,384,512}x512.png` plus a maskable 512 variant, rendered from the existing `favicon.svg` brand mark via headless Chrome (no new icon asset existed before this pass) — `src/assets/manifest.webmanifest` references them for home-screen install on both iOS (`apple-touch-icon` in `index.html`) and Android/other (the manifest's `icons` array, `any` + a dedicated `maskable` entry with safe-zone padding).
- **Image loading**: `loading="lazy" decoding="async"` added to the puzzle board's 9 piece tiles and the avatar (non-critical, revealed progressively); `loading="eager" decoding="async" fetchpriority="high"` on the completion screen's full reveal image (the opposite case — it's the payoff moment, must not be deprioritized). `decoding="async"` added everywhere else images exist (Wizard's crop preview, Creator Preview's completion screen) for consistency, even where the gain is marginal (local blob URLs).
- **Firebase reads — the other real gap this phase found.** `FirestoreExperienceRepository.listByCreator()` (the Dashboard's one query) was fetching every result's `puzzle_experiences_private` doc via an individual `getDoc` per experience — an N+1 read pattern (1 query + N reads for a creator with N puzzles) for data the Dashboard never uses: `ExperienceCardComponent` and `dashboard.rules.ts` only ever read public fields (`occasion`, `recipientDisplayName`, `status`, `createdAt`/`publishedAt`/`completedAt`). Fixed to read only `puzzle_experiences` — one query, zero extra reads, regardless of how many puzzles a creator has. `getById()` (the Wizard's read, which genuinely needs `questions`/`completionMessage`/etc) is untouched — this was never a general "read less" pass, just removing a read nothing consumed.
- **Signal recomputation**: `PuzzleBoardComponent` was re-reading `PuzzleSessionFacade.publicMeta()` and rebuilding a `'url(...)' ` string inline in the template, once per locked tile (up to 9× per change-detection run, for a value identical across all of them). Hoisted into a single `lockedPatternStyle` computed signal read once and shared. The rest of the Signal graph (`PuzzleSessionFacade.score()`/`isComplete()`, the Wizard/Preview facades) was already using `computed()` correctly — Angular Signals memoize on their own, so this was the one place doing avoidable extra work, not a systemic issue.
- **Animation performance**: every `@keyframes` block in the app (question modal, welcome screen, both completion screens, puzzle board unlock, share panel) already animated only `opacity`/`transform` — compositor-friendly, no layout-triggering properties, confirmed by an audit of every stylesheet with a keyframe rule. Two of those animated elements (`share-panel.component.scss`'s success state, Creator Preview's `completion-screen.component.scss` reveal image) were missing an `@media (prefers-reduced-motion: reduce)` override that every other animated component already had — added to match, so motion-sensitive users get the same treatment everywhere, not just in the M4 Recipient flow.
- **Bundle size**: production build (`ng build --configuration production`) reports an initial bundle of 1.34 MB raw / ~292 KB estimated transfer, and lazy per-page chunks ranging 2–45 KB raw — within the existing 1.35 MB warning / 1.6 MB error budget (`angular.json`) without needing to raise it this time. Every Firebase SDK and Ionic component import in the app was already using tree-shakeable modular imports (`@angular/fire/firestore`, `@ionic/angular/standalone`, etc., never the barrel `@angular/fire` or `IonicModule`) before this phase started — confirmed by audit, nothing to change.
- **Low-end mobile devices — verified indirectly, not on physical hardware.** This sandboxed environment has no real Android/iOS low-end device and no Lighthouse/CPU-throttling tooling installed; claiming a verified-on-device result would not be honest. What IS verified: initial transfer size (~292 KB) is well within budgets commonly used as a "reasonable 3G/low-end" ceiling, every animation is GPU-compositable, and the service worker now caches the app shell so a repeat visit is instant regardless of network. **Recommended before launch**: a real Lighthouse mobile run (or a physical low/mid-range Android device) against the deployed Hosting URL, particularly for Time-to-Interactive under CPU throttling — tracked as a known limitation, not silently skipped.

## Firebase project

This app shares the **`lovedigitally-app`** Firebase project with `/lovedigitally-web` — it does not have its own project. Isolation comes from:

- A `puzzle_*` Firestore/Storage namespace (`puzzle_creators`, `puzzle_experiences`, `puzzle_experiences_private`, `puzzle_progress`, `puzzle_events`, `puzzle_storage/...`) that never collides with `lovedigitally_pages` / `lovedigitally_orders` / `lovedigitally_subscriptions` / `lovedigitally_webhook_events`.
- A dedicated Hosting site target, `puzzle-module` (see `.firebaserc`), so this app deploys to its own URL without touching the existing static site's Hosting config.
- A dedicated Functions **codebase**, `puzzle-module` (see `firebase.json`), so `firebase deploy --only functions:puzzle-module` never touches `publishPage` / `createOrder` / `verifyOrder` / `createSubscription` / `verifySubscription` / `razorpayWebhook`.

### ⚠️ Rules files are shared, not duplicated

`firestore.rules` and `storage.rules` in this directory are **symlinks** to `../../lovedigitally-web/firestore.rules` and `../../lovedigitally-web/storage.rules` — not copies. The Firebase CLI refuses to reference a rules file outside the current project directory (verified directly against the emulator while building M2 — not an assumption), so a symlink is what lets both apps' `firebase.json` point at one physical, single-source-of-truth file without the CLI's path restriction getting in the way, and without a real risk of the two copies drifting apart (they're the same inode).

**As of M2**: the `puzzle_*` match blocks are merged into `lovedigitally-web/firestore.rules` and `lovedigitally-web/storage.rules`, and both are covered by real emulator tests (`functions/src/emulator-tests/security-rules.emulator-test.ts`) — not just written, verified. Real `firebase deploy` still needs to run from `lovedigitally-web/` (or with an explicit `--config`), since that's where the physical files live and where the Firebase CLI's project-directory check is satisfied natively.

### Real Firebase config

`src/environments/environment.ts` and `environment.prod.ts` contain **placeholder** values for the `lovedigitally-app` web config — real values (`apiKey`, `appId`, `messagingSenderId`) were not available when this scaffold was generated and must never be hand-typed into these files from memory or guesswork. Pull them from Firebase Console → `lovedigitally-app` → Project Settings → your web app, and inject them at build/CI time (e.g. a CI secret that does a token-replace on `environment.prod.ts` before `ng build --configuration production`). Local dev against the emulators does not need real values at all — the emulator suite ignores `apiKey`.

## Architecture at a glance

```
src/app/                                                             (the Angular app)
├── domain/          framework-free models, rules, ports        (M1, extended in M2–M4)
├── infrastructure/  Firebase adapters implementing those ports  (M3, M4)
├── application/     use-cases & Signal-based facades            (M3, M4)
├── features/        routed Ionic pages/components                (M3, M4)
├── shared/          dumb, reusable UI atoms                      (M3+)
└── core/            guards, error handling                       (M3+)
```

## CI

`.github/workflows/puzzle-module-ci.yml` (repo root) lints, builds, and tests both this app and `functions/` — including `functions/`'s real emulator test suite, not just its mocked unit tests — on any push/PR touching `apps/puzzle-module/**` or the shared `lovedigitally-web/firestore.rules` / `storage.rules`. It's scoped by path so it never runs against unrelated changes elsewhere in this monorepo.
